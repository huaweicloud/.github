## 3. Creation Process

### 3.1 Full Flow

```
Developer submits Issue (select "New Repository Request" template)
    │  Fill in 12 fields: language, type, name, description, visibility, license, Topics, roles, justification, checklist
    │
    ▼
Form validation (repo-request-validation.yml)
    │  repo_request_validator.py checks:
    │  ├── Repo name format (lowercase+digits+hyphens, ≤100 chars, no consecutive hyphens)
    │  ├── Category/type matching
    │  ├── Topics ≥ 3, each matching [a-z0-9][a-z0-9.-]*
    │  └── Owner 1-2 people, Maintainer 2-3 people
    │
    ├── Invalid → comment with specific errors + no approval (no status/pending)
    │            user edits and resubmits → re-validate
    │
    └── Valid → add status/pending label + comment "awaiting approval" + Feishu notify admin
            │
            ▼
        Admin review (approve-repo.yml / reject-repo.yml)
            ├── Approve → run approve-repo.yml → add status/approved label
            │           ↓
            │      repo-creator.yml workflow triggers (on: labeled, status/approved)
            │           ↓
            │      Creation bot runs (repo_creator.py):
            │
            │      ├── 1. Parse form → extract 12 fields (Chinese/English compatible)
            │      ├── 2. Validate (secondary in-script validation)
            │      │   ├── Repo name format
            │      │   ├── Category/type match
            │      │   ├── Topics ≥ 3 (invalid topics silently dropped)
            │      │   └── No duplicate repo
            │      ├── 3. Create repo (BOT_TOKEN, repo-scope PAT)
            │      │   ├── Set description, visibility (public/private)
            │      │   ├── auto_init=True
            │      │   ├── Issues on, Projects off, Wiki off
            │      │   ├── Squash merge on, Merge/Rebase commits off
            │      ├── 4. Init files (by type tier + language, see §3.3 matrix)
            │      ├── 5. Create label system (product 14 / sample 8)
            │      ├── 6. Set Topics
            │      ├── 7. Enable security alerts + auto-fix (Dependabot, skip internal)
            │      ├── 8. Configure repo-level Secrets (BOT_TOKEN + GITCODE_TOKEN)
            │      │   ※ org-level secrets unreliable for new repos, written explicitly
            │      ├── 9. Assign roles
            │      │   ├── Owner → admin
            │      │   ├── Maintainer → maintain (not duplicate with Owner)
            │      │   └── Writer → push (not duplicate with Owner/Maintainer)
            │      ├── 10. GitCode sync creation (api.gitcode.com/api/v5, metadata consistent)
            │      ├── 11. Close Issue (report comment + status/completed + close)
            │      └── 12. Feishu notification (interactive card)
            │
            └── Reject → run reject-repo.yml → comment reason + status/declined label
                        ↓
                     manually close Issue
```

### 3.2 Creation Form Fields

| # | Field | Type | Required | Description |
|---|------|------|:--:|------|
| 1 | Init language | dropdown | ✅ | 中文 / English, determines init template language |
| 2 | Repository type | dropdown (9 options) | ✅ | Combined (category/project): Product/SDK, Product/Terraform Provider, Product/GitHub Action, Product/Framework Integration, Product/Exporter/Plugin, Product/IoT SDK, Sample/Lab/Sample, Documentation/Docs/Dataset, Internal/Internal Config |
| 3 | Repository name | input | ✅ | Regex: `[a-z0-9]([a-z0-9-]*[a-z0-9])?`, ≤100 chars, no consecutive hyphens |
| 4 | Description | textarea | ✅ | Used for GitHub Description |
| 5 | Visibility | dropdown | ✅ | public / private |
| 6 | License | dropdown | ✅ | Apache-2.0 (recommended) / MIT / BSD-3-Clause (user choice for Product only; others forced Apache-2.0) |
| 7 | Topics tags (≥3) | textarea | ✅ | ≥3, comma/newline separated; each matching `[a-z0-9][a-z0-9.-]*` |
| 8 | Owner (1-2 people) | textarea | ✅ | GitHub usernames, comma separated, strictly 1-2 |
| 9 | Maintainer (2-3 people) | textarea | ✅ | GitHub usernames, comma separated, 2-3 |
| 10 | Writer | textarea | | Optional |
| 11 | Justification | textarea | ✅ | Background, problem solved, target users |
| 12 | Confirmation checklist | checkboxes | ✅ | 6 items: naming/no-duplicate/members/governance |

> Chinese form `create-repo.yml`, English form `create-repo.en.yml`. English form uses English field labels and combined type options (Product/SDK, Sample/Lab/Sample, etc.).

## 4. Approval Process

```
Issue created
    ↓
Form validation (repo-request-validation.yml)
    ├── Valid → add status/pending → await approval
    └── Invalid → comment errors → user fixes → re-validate
    ↓
Admin review (workflow_dispatch)
    ├── Approve → run Approve Repo Request workflow
    │           ↓
    │      add status/approved label
    │           ↓
    │      repo-creator.yml triggers (on: labeled, label=status/approved)
    │           ↓
    │      checkout → run scripts/repo_creator.py
    │           ↓
    │      auto-create + init + security alerts + GitCode sync + Feishu notify + close Issue
    │
    └── Reject → run Reject Repo Request workflow
                ↓
             comment reason + status/declined label
                ↓
             manually close Issue
```

## 5. GitCode Sync Creation

- Uses GitCode v5 API (`https://api.gitcode.com/api/v5`)
- Creates same-named repo on GitCode at creation: `POST /orgs/huaweicloud/repos`
- **Metadata consistent**: GitCode repo visibility (private/public) and description match GitHub; if repo already exists, use `PATCH` to update metadata
- New repos get `sync-to-gitcode.yml` workflow (`oauth2:token` auth; GITCODE_TOKEN written as repo secret by the creation process)
- Subsequent pushes auto-sync to GitCode

## 6. Secrets Configuration

### 6.1 Secrets required by the creation bot (repository-requests repo level)

| Secret | Purpose |
|--------|------|
| `BOT_TOKEN` | repo-scope PAT for creating org repos + approve/reject labeling + writing secrets to new repos |
| `GITHUB_TOKEN` | auto-injected by workflow, for Issue comments and labels |
| `GITCODE_TOKEN` | GitCode API auth (GitCode sync at creation + writing to new repos) |
| `GITCODE_USERNAME` | GitCode username |
| `FEISHU_APP_ID` | Feishu app ID |
| `FEISHU_APP_SECRET` | Feishu app secret |
| `FEISHU_ADMIN_OPEN_ID` | Feishu notification recipient open_id |
| `SMTP_HOST/PORT/USER/PASS` | Email notification (SMTP) |
| `EMAIL_REPORT_TO` | Report recipient email |

### 6.2 Repo-level Secrets auto-configured for new repos (setup_repo_secrets)

> **Important**: org-level secrets do not reliably propagate to new repos (verified). Therefore `setup_repo_secrets()` writes the following **repo-level** secrets for each new repo:

| Secret | Purpose |
|--------|------|
| `BOT_TOKEN` | so triage workflows can checkout and run `.github/actions/issue-bot` |
| `GITCODE_TOKEN` | so `sync-to-gitcode.yml` push auth succeeds |

### 6.3 Config-center Secrets (.github repo level)

The `.github` governance workflows (SLA/weekly/monthly/notify etc.) use **repo-level** secrets: `BOT_TOKEN`, `FEISHU_APP_ID/SECRET/ADMIN_OPEN_ID`, `GITCODE_TOKEN/USERNAME`, `SMTP_HOST/PORT/USER/PASS`, `EMAIL_REPORT_TO`.

> Note: org-level secrets also don't apply to the special `.github` repo; it configures repo-level secrets separately.

## 7. Admin Quick Reference

```powershell
# View pending requests (status/pending)
gh issue list -R huaweicloud/repository-requests -l "status/pending"

# Approve creation
gh workflow run "Approve Repo Request" -R huaweicloud/repository-requests \
  -f issue_number=<number>

# Reject creation
gh workflow run "Reject Repo Request" -R huaweicloud/repository-requests \
  -f issue_number=<number> -f reason="reason"
```
